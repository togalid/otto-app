# Ottoの公開と収益化の検討方針

更新日：2026年11月9日

対象は `sound-playground/` の音楽アプリOtto。親ディレクトリの自由研究ノートアプリとは独立した検討である。

現時点の有力案は、**基本の演奏・セッションを無料Web版で提供し、Stem分離と作り込む機能を有料ローカル版で提供すること**。別の開発チャットでも、機能設計・公開準備の参考にする。

これは検討方針であり、価格、製品仕様、開発順序、発売日を確定したものではない。この文書だけを根拠に、課金、クラウド送信、デスクトップ化、無料機能の制限を実装しない。既存の開発ルールと、その時点のユーザー依頼を優先する。

## ユーザーの意向

- 将来的に無料で公開し、気に入った利用者向けの有料商品で収益化したい。
- 長時間のセッションによって運営側の処理費用が増え続けないなら、基本機能は無料でよい。
- 「Stem機能＋作り込む機能」をローカル版として有料販売する案を検討している。
- 販売経験がないため、配布・保守・サポートを含めて無理のない形で始めたい。

## 現在の実装と費用の関係

2026年11月9日時点のコードに基づく。実装変更時には再確認する。

| 機能 | 実行場所と仕組み | 運営費への影響 |
| --- | --- | --- |
| Ottoの自動演奏・応答 | ブラウザ内。コード、スケール、ユーザーのフレーズ、音のつながり、スタイル、乱数などのルールで音を選ぶ | 外部AI API料金は発生しない。演奏時間に比例するクラウド計算は行わない |
| 伴奏・発音 | 利用者の端末のWeb Audio／Tone.js | 利用者側のCPU・電力を使う |
| Web版の読み込み | HTML、JS、CSSなどのファイル配信 | 配信費用・サービスの制限はある。演奏を音声ストリーミング配信する構成ではない |
| Stem分離 | ブラウザからローカルの `/api/stems` へ音声を渡し、NodeがDemucsの `htdemucs` をCPU実行する | 現在は同じPCで処理。クラウドへ移せば計算・転送・保存等の費用が生じる |
| 分離済みStemの再生 | ブラウザ内の音声バッファ | 繰り返し再生するたびに分離をやり直す構成ではない |

主な根拠：[演奏・応答](../dist/buddy.js)、[音声処理](../dist/audio.js)、[音源読み込み](../dist/reference-player.js)、[Stemサーバー](../server/stems.mjs)、[README](../README.md)。

現在のStemサーバーはlocalhostのホスト・Originを限定している。公開ドメインにそのまま置いて提供できるAPIではない。現在の開発ルールも、外部AI呼び出しや参照音源の外部アップロードを禁止している。

無料Web版でも、ドメイン、配信、保守、問い合わせ対応の費用・工数は残る。静的ホスティングの無料枠を利用する案があるが、「永久に運営費ゼロ」とは約束しない。アカウント、クラウド保存、分析等を追加する際は個別に見積もる。

## 無料Web版と有料ローカル版の分け方

無料版では、Ottoを好きになるまで十分に遊べることを重視する。有料版は、好きな曲で練習し、自分の演奏や編曲を残す用途を深める。

以下は機能候補であり、すべて実装済み・実装決定という意味ではない。

| 項目 | 無料Web版の案 | 有料ローカル版の案 |
| --- | --- | --- |
| 基本体験 | 登録なしですぐ演奏・セッション | 同じ演奏体験を引き継ぐ |
| マジック鍵盤・基本伴奏 | 十分に使える。演奏時間による制限は原則不要 | 共通機能として提供 |
| Stem分離 | 初期公開では対象外とする案 | 利用者のPC内で処理 |
| 作り込み | 基本調整 | 区間ごとの編曲、奏法・音色の詳細編集など |
| 保存 | 基本設定の持ち運び | 曲・編成・編集状態を再開できるプロジェクト管理 |
| 制作への接続 | 範囲未定 | 録音、音声・MIDI書き出しなど |
| オフライン | 初期は保証しない | モデルの初回取得などを含め、対応範囲を定義する |

既に提供している編集・保存機能を、この表に合わせて勝手に削除・有料化しない。境界は利用者の反応を見て決定する。

想定する有料体験は、「好きな曲を読み込む → Stemを選んで一緒に演奏する → 編曲や設定を調整する → 保存して翌日も続ける → 必要なら演奏を書き出す」。Stem単体ではなく、Ottoとの演奏につながる一連の体験として商品化する。

## Full版での開発と無料版の切り替え

通常の開発は、有料提供候補も含めたFull版を対象にする。ユーザーが依頼した機能をFull版で完成させ、無料公開時に提供範囲を選ぶ。全機能を先回りして実装する意味ではない。

提供表は [dist/features.js](../dist/features.js) にある。通常の `npm run dev` はFull版、`npm run dev:free` は無料版プレビュー、静的配信は無料版を選ぶ。現在の切り替え対象はStem分離のみ。

- 無料版とFull版でリポジトリや長期ブランチを分けず、音楽エンジン・画面の共通コードを保つ。
- 機能IDごとの提供表を一か所に置く。例えば基本セッション、Stem分離、詳細編曲、録音、書き出しを個別に扱う。単一の `isPaid` 条件を各画面へ散在させない。
- 開発用Full、無料版プレビュー、公開Web、公開ローカル版の設定を区別する。普段は開発用Fullで動かし、無料版も独立した起動設定等で確認できるようにする。公開物は提供範囲を明示し、設定不足時にFullへ自動的に切り替えない。
- 提供プランと実行環境を区別する。Fullであっても、Demucsの未導入などで使えない機能はある。「プラン対象外」と「環境未対応・準備不足」を別の状態として扱う。
- 画面の表示と処理の入口で、同じ機能定義を参照する。メニューを隠すだけでなく、ショートカットや設定読み込みなど別経路からの実行も考慮する。
- 開発用の切り替えは購入権限の検証ではない。公開版に誰でもFullへ切り替えられる開発スイッチを残さない。ライセンス方式が決まった段階で必要な検証を処理側へ追加する。ブラウザのフラグだけを有料機能の保護に使わない。
- 無料Web版にはローカル専用の実行物・モデルを含めず、依存モジュールも必要に応じて分離する。現在はビルドなしの構成なので、配布対象の選別方法は公開準備時に設計する。
- Full版で保存した設定を無料版で開いても、有料専用の設定を黙って削除・上書きしない。再現できない機能を知らせ、保持または元ファイルを保護した別保存を行う方針とする。

導入後は、Full版の機能に加え、無料版で基本セッションが成立すること、対象外処理が実行されないこと、Full設定の読み込みでデータを失わないことを確認する。新機能の無料／有料区分は提供表で明示し、未分類の機能を公開Webへ自動追加しない。

公開前に、無料版へ含める機能と配布ファイルを確認する。購入権限の設計は販売方式の決定時に行う。

## 課金方式の候補

最初は買い切りを有力候補とする。処理が利用者のPCで完結するなら、利用量に応じたクラウド計算費を理由にサブスクへする必要はない。

- 価格は未定。会話中の4,980円は仮例であり、決定価格・検証済み相場ではない。
- 購入対象の機能・バージョン、不具合修正、大型アップグレードの扱いを定義する。
- 将来の全機能を永久無料で提供する約束はしない。
- 購入済み機能の継続利用、オフライン時のライセンス確認、販売サービス終了時の扱いを検討する。
- サブスクは、継続コンテンツやクラウド処理など、継続して提供する価値が必要になった場合に再検討する。

## StemをWebで提供する場合の代替案

「WebではStemが不可能」という意味ではない。有料ローカル版が有力案だが、次の選択肢もある。

| 方法 | 特徴 | 判断に必要なこと |
| --- | --- | --- |
| クラウドで分離 | インストール不要。音源送信と運営側の計算費が発生 | 費用、利用上限、保存・削除、送信への同意、公開APIの設計 |
| ブラウザ内で分離 | 利用者側で計算。モデル配信は必要 | モデル互換性、速度、品質、メモリ、端末・ブラウザ差の実測 |
| ローカルアプリで分離 | 利用者側で計算し、ローカルのファイル管理と統合できる | モデル導入、対応OS、性能、アプリ配布・更新の設計 |

ONNX Runtime Web等はブラウザ内推論を提供するが、現在のDemucsがそのまま動くわけではない。Ottoでのブラウザ内分離の実用性は未検証。

## 開発時に考慮すること

- Web版とローカル版で演奏エンジン・音楽ルールを共有し、二重実装を避ける。
- ファイル管理、Stem実行、ライセンス等の環境依存処理を分離する。デスクトップ技術は未定で、親アプリがTauriであることだけを採用理由にしない。
- 現在の設定ファイルとの互換性を維持し、Webからローカルへ移行しやすくする。
- 初回モデル取得、容量、分離の進捗・キャンセル・失敗復帰を、購入者がNodeやPythonを設定せずに使える体験へ整える。
- 対応OS・CPU・メモリ・音源の長さを実測して定義する。デスクトップ化だけで高速化・低遅延になるとは限らない。
- 現状の音声・Stemはメモリ内で、設定JSONに原曲や生成音声は含まれない。作業再開にはプロジェクト保存の設計が別途必要。
- 一般配布前に、同梱コード・モデル・音色素材等のライセンス、配布・販売条件を確認する。

## 公開と販売の進め方の案

1. 想定ユーザーに少人数で試してもらう。候補は、鍵盤を持っているが一人では続かない人や、気軽に伴奏と演奏したい人。
2. 無料Web版を公開する。対応環境と利用できる機能を明示し、演奏開始・再訪・よく使われる機能を確認する。
3. ローカル版の最小体験として、音源読み込み、Stem選択、セッション、保存・再開を完成させる。対応OSは検証できる範囲に絞る案。
4. 継続利用者にローカル版を試してもらい、価格と購入意向を検証する。意向調査だけでなく、完成した商品の実購入で確かめる。
5. 販売・更新・問い合わせ対応を整えて発売し、要望に応じてOSや制作機能を広げる。

## 未決事項

- 最初の対象ユーザーと、一番強く伝える利用体験。
- 無料／有料の具体的な機能境界と、ローカル版の最小発売範囲。
- Macのみから始めるか、Windowsも対象にするか。
- デスクトップの実装方式とStemモデルの配布方法。
- 保存形式、原曲・Stemの保存先、容量管理、録音・書き出しの範囲。
- 価格、更新方針、返金・サポート方針、決済・ライセンス・販売経路。
- 署名・公証等の配布準備、更新方式、保守費用。
- Web公開先、ドメイン、公開時の対応ブラウザ、MIDI・音声の実機検証。
